# THE CLONKER 10000

## Architecture & Pseudocode Notes

*Integrated working design — October 8, 2026*

> **Design mantra:** Clonker controls actions, not brands — and devices own their own state.

## Core Philosophy

Clonker is first and foremost a tactile input device. It translates physical actions into generic events and routes those events to configurable network commands. The controlled TV, AVR, streamer, and other devices remain authoritative for their own state. Avoid recreating an old-style universal remote that attempts to remember every device's power, input, and volume state.

Modern network APIs and HDMI-CEC can coordinate much of the entertainment system. ARC/eARC is principally an audio-return path; HDMI-CEC is the control protocol. Do not confuse the two.

## Current Controller and Development Environment

**Active bench controller:** Adafruit Feather ESP32 V2 (PID 5400), classic ESP32, running **CircuitPython 10.3.1**. It replaces the Unexpected Maker FeatherS3[D] as the current development board. The original FeatherS3[D] stopped enumerating over USB and became unusually hot; the cause remains unknown, and it should not be powered for further experiments without resolving the fault.

The Feather ESP32 V2 has a USB-to-serial bridge, so it does **not** mount a `CIRCUITPY` USB storage drive. CircuitPython was flashed successfully using Adafruit's WebSerial ESPTool; a Windows COM-port REPL also worked. Routine development is now **iPad-first**:

1. Write or maintain Python in **Textastic**.
2. Use CircuitPython **Web Workflow** from iPad Safari over local Wi-Fi to transfer/edit files and access the serial terminal.
3. Save `code.py` and allow auto-reload, or use Ctrl+D in the REPL to restart it. Ctrl+C interrupts running application code and enters the REPL.
4. Keep the working standalone power arrangement (known-good Apple USB adapter) while the electronics are under development.

The Web Workflow file-browser editor works; its separate full editor has sometimes stalled. Safari's serial terminal has sometimes appeared greyed out until a refresh triggered a delayed HTTP authentication challenge. These are development-interface quirks, not evidence of a failed board.

The board has been reachable at `192.168.50.3` on the local network, but this is a **DHCP address, not a guaranteed permanent address**. The `CIRCUITPY_WIFI_HOSTNAME = "clonker"` setting was readable with `os.getenv()`, yet the running hostname and Web Workflow welcome page still displayed an autogenerated `cpy-...` hostname after power cycling. `clonker.local` was not working; use the IP until this is understood. A similar hostname bug reported for other CircuitPython boards does not prove the Feather V2 has the same cause.

Never commit real `settings.toml`, Wi-Fi credentials, passwords, or tokens to this public repository.

## Four Kinds of State

| State | Examples | Source of truth |
|---|---|---|
| **Physical** | Three-position room selector, maintained switches | Read hardware/GPIO |
| **Configuration** | Room names, endpoints, HTTP actions, preferences | Persistent flash file |
| **Device** | AVR volume, TV input/power, Roku application | Query controlled device when needed |
| **Ephemeral** | Debounce, idle timer, temporary OLED message, menu position | RAM while running |

**Do not maintain duplicate truth unless there is a compelling reason.** The room selector is its own memory: there is no reason to write its position to flash on every movement.

## Three-Room Model

V1 supports up to three logical rooms because its maintained physical selector has three positions. Internal identities `Room1`, `Room2`, and `Room3` map to configurable display names such as `DEN`, `SUN`, and `AUX`.

```text
ROOM 1 -> configurable name -> Media endpoint + AVR endpoint
ROOM 2 -> configurable name -> Media endpoint + AVR endpoint
ROOM 3 -> configurable name -> Media endpoint + AVR endpoint
```

On startup or wake from deep sleep, read the selector's actual position. A three-position side switch is the current candidate; the exact physical mapping and final hardware remain subject to testing.

## Generic Physical Actions

Translate input hardware into device-independent actions **before** looking up network commands:

```text
NAV_UP       NAV_DOWN      NAV_LEFT      NAV_RIGHT
NAV_SELECT   BACK          HOME
REWIND       PLAYPAUSE     FFWD
VOLUME_UP    VOLUME_DOWN   MUTE
POWER        MODE_1        MODE_2        MODE_3
STATUS       INFO
```

The hardware reports *what the human did*. Configuration determines *what it means for the selected room*. An action can be deliberately unmapped for a particular room.

## Configurable Network Commands

Each room/action mapping can specify an HTTP method, URL, and optional request body. Headers or richer authentication can be added when a real device requires them. Keep the initial system small; do not build Postman into the remote.

```text
Room1.Media.Home:
    method: POST
    url: http://<media-device>/keypress/Home

Room1.Media.Up:
    method: POST
    url: http://<media-device>/keypress/Up

Room1.AVR.VolumeUp:
    method: GET
    url: http://<avr-device>/<configured-command>
```

These are conceptual examples, not verified addresses. Roku, Denon, LG, and other device-specific command formats must be tested against actual equipment.

### Prefer the authoritative device

If a Denon AVR controls speaker volume, prefer addressing it directly rather than sending volume through a TV and relying on CEC as an intermediary. Another installation might deliberately send volume to the television or soundbar. **Configuration wins; do not hard-code a brand or routing choice.**

## Persistent Configuration and Files

CircuitPython loads persistent configuration from nonvolatile flash at boot. Flash survives complete power loss; transient RAM does not. The current format is **not locked**. We want to experiment with an XML file written from a web form, while keeping JSON as a valid alternative if it proves easier to parse reliably in CircuitPython.

Conceptual flash layout (not a USB-mounted drive on the current V2 board):

```text
/
    code.py
    settings.toml            # private Wi-Fi / Web Workflow bootstrap
    clonker_config.xml       # room mappings and preferences (experiment)
    sounds/
        clonk.wav
        startup.wav
```

Do not commit `settings.toml` or secrets. Provide a sanitized `settings.example.toml` if needed. The configuration file should be inspectable, exportable, backed up, and restored. Avoid writing flash for every button press or every unchanged setting; validate changes and save only when needed.

## Configuration Interface: Onboard Web Page First

**Updated near-term direction:** Prototype a small **Clonker-hosted HTML form** before building a full iOS Shortcut configuration interface. The user should be able to open the Clonker in iPad Safari, enter text, save it, and verify that it persists after power removal.

The application HTTP server is distinct from CircuitPython's built-in Web Workflow server. Proposed development addresses:

```text
http://<clonker-ip>/             CircuitPython Web Workflow (port 80)
http://<clonker-ip>:8080/        Clonker application configuration page
http://<clonker-ip>:8080/api/... Clonker application endpoints
```

Port 8080 is a proposal, not yet tested. `clonker.local` must not be assumed to work until the hostname issue is resolved.

```text
iPad browser / optional iOS Shortcut
              |
              | HTTP request on trusted home LAN
              v
       Clonker application server
              |
              +--> display current values
              +--> accept text form submission
              +--> validate and XML-escape values
              +--> update RAM configuration
              +--> write XML to flash
              +--> respond with success/error
              |
              v
       Reboot -> reload persisted XML
```

Keep ordinary configuration updates separate from firmware/code updates. Avoid placing passwords in URL query strings. A LAN-only prototype is **not** a secure public-facing management service; do not forward its port to the internet. Later, authentication and safer write/backup behavior may be appropriate.

An iOS Shortcut remains a possible client of the same API, not a discarded idea. The user already has home-theater Shortcuts that may help when designing mappings.

### First configuration-page milestone

A minimal form with `Room name`, `Button label`, and `Device URL` is enough to prove browser -> HTTP POST -> XML file -> reboot -> reload. Only then expand to all rooms, endpoints, and action mappings.

## Power, Wake, and System Control

**Clonker's own sleep state is separate from the theater's POWER action.** The guarded SYSTEM/POWER button is a logical input, not a battery-disconnect switch. It may send a configurable room POWER command when the Clonker is awake.

### Proposed V1 three-state behavior

```text
             User activity
                  |
                  v
               ACTIVE
        commands / OLED / Wi-Fi
                  |
             short idle
                  v
             LIGHT SLEEP
     supported input wakes and acts
                  |
       longer inactivity (~10 min
       candidate; not finalized)
                  v
             DEEP SLEEP
        OLED off / Wi-Fi off
                  |
       first supported button press
                  v
         WAKE-ONLY FRESH BOOT
       reload config + read selector
       reconnect Wi-Fi + show ready
                  |
                  v
               ACTIVE
      next press executes command
```

**ACTIVE:** Handle controls, network requests, OLED, audio, and configuration HTTP requests. User activity resets the inactivity timer.

**LIGHT SLEEP:** After a configurable short idle interval, use supported GPIO alarms to wake. The design goal is **one press, one action**: the button press that wakes the Clonker should also execute its mapped command. If Wi-Fi has disconnected, reconnect before sending the command. Do not assume Wi-Fi stayed usable during sleep. Encoder turns are more difficult than held buttons: brief quadrature pulses might wake the ESP32 without retaining reliable direction or step count. Bench-test before promising this behavior.

**DEEP SLEEP:** After longer inactivity (initial thought: roughly ten minutes), show a brief sleep message, dim the OLED if supported, switch its display off, and enter deep sleep. The **first eligible button press wakes only**; it must not send a room command. Deep sleep causes a fresh CircuitPython boot. Load persistent configuration, read the physical selector, reconnect Wi-Fi, and signal readiness. The *next* button press sends the command. This deliberately simplifies V1; we do not need to preserve the initiating command across the reboot.

**SYSTEM/POWER safety:** A wake-only press from deep sleep must **never accidentally toggle theater power**. When active, the guarded SYSTEM/POWER button can dispatch the configured `POWER` action for the currently selected room. The remote does not automatically assume or remember whether that room is already on.

### OLED and audio personality

Ideas include a brief `I'M ASLEEP!` message, stepwise contrast fading, display-off, and a grumpy wake sound (`WHO DISTURBS MY SLUMBER?`). Avoid long sound effects that delay the first actionable command. An OLED display-off command may leave some module electronics powered; measure this rather than assuming zero current.

A motion-sensor interrupt, similar in spirit to older activity-aware remotes, is a possible later enhancement. It is **not** a V1 dependency.

### Deep sleep is not fully off

Deep sleep keeps limited wake circuitry powered and normally restarts the Python program when awakened. Full power-off requires separate switching circuitry and cannot wake itself without an external power-control path. The Feather board's regulator and other components also draw current, so **whole-board** deep-sleep current can exceed ESP32 chip-only specifications. Final timeout and battery-life claims must come from measurement.

Not every GPIO is a valid wake source in every sleep mode. Verify wake-capable pins and polarity before assigning final controls. A wake-only press cannot reliably mean *any* button until the input circuit and wake constraints are tested.

### Network availability

The app HTTP server and Web Workflow should not be expected to remain reachable during deep sleep. Light sleep may also interrupt network service. The firmware should test/reestablish connectivity on wake as needed. A future status page can report boot count, Wi-Fi reconnect count, uptime, and measured time to first network command.

A previous virtual-button program printed `SIMULATED LIGHT SLEEP` repeatedly every thirty seconds while idle. A proper state machine should log the transition only once. Pressing Ctrl+C interrupts the running `code.py`; it is not a failure.

## OLED and Hardware Integration Order

The display moves **ahead of the first physical button** in the bench plan:

1. Inspect and connect one of the two existing **0.49-inch 64x32 SSD1306 I²C OLEDs**. Verify its actual pin labels, header soldering, and 3.3V compatibility.
2. Show a basic startup banner, Wi-Fi status, and IP address.
3. Experiment with contrast fading, status screens, and display-off.
4. Evaluate a larger **1.3-inch 128x64 SH1106 I²C OLED** as a final-panel candidate. A Hosyond five-pack listing was identified; purchase/arrival is not yet confirmed here. SH1106 requires its appropriate CircuitPython driver rather than assuming the SSD1306 driver.
5. Wire a simple wake-capable GPIO button and test light-sleep wake/dispatch.
6. Test timed deep sleep, reboot behavior, and Wi-Fi reconnect latency.
7. Add encoders, room selector, other buttons, and audio incrementally.

Current inventory includes Dupont jumpers, solid-core 22-AWG wire, a large breadboard, and other test leads. The four-wire OLED interface is `3V`, `GND`, `SDA`, and `SCL`; inspect actual module markings before applying power. Loose header pins may require soldering.

## Control Hardware and Audio

The working hardware plan includes a large Grayhill optical volume encoder and metal knob; smaller Bourns selector encoder and black knob (with a finite-stop rotary selector still under consideration); navigation controls; large HOME/BACK buttons; small auxiliary metal buttons; a guarded momentary SYSTEM control; and a three-position side room selector. Final mechanical layout is not fixed.

The Adafruit piezo can provide simple beeps. A MAX98357A I²S amplifier and small speaker can support richer sounds and Clonker's startup/grumble personality. The final sound scheme, GPIO assignments, and power budget remain experimental.

Momentary buttons generally connect between GPIO and ground with internal pull-ups, using tiny logic currents. Switch current ratings describe maximum capability, not current drawn. A 12/24V-rated illuminated ring must **not** be powered directly from an ESP32 GPIO; its lighting needs appropriate separate voltage/current handling.

## Runtime Flow

```text
Physical input / wake event
            |
            v
Determine ACTIVE / LIGHT_SLEEP / DEEP_SLEEP wake context
            |
            +--> deep-sleep wake-only? -> boot/ready, NO device command
            |
            v
Debounce / decode button or encoder
            |
            v
Generate generic action
            |
            v
Read maintained room selector
            |
            v
Look up room/action configuration
            |
            v
Ensure Wi-Fi and send configured HTTP request
            |
            v
Device owns resulting device state
```

Conceptual dispatch pseudocode:

```python
def selected_room():
    if selector_is_position_1():
        return "Room1"
    if selector_is_position_2():
        return "Room2"
    return "Room3"


def handle_action(action):
    room = selected_room()
    command = config[room]["actions"].get(action)
    if command is not None:
        ensure_wifi()
        send_http(command)
```

This is illustrative pseudocode, not ready-to-run code. The hardware and network helper functions are still to be implemented.

## Why Not an Old-Style Universal Remote?

Older remotes encouraged separate TV/AVR/DVD/cable power and input modes, macros, and remote-side guesses about state. Clonker should not become the brains of the home theater. It should be an unusually satisfying physical control surface that sends the right actions to equipment that already knows its own state.

## V1 Design Guardrails

- Three rooms maximum, matching the physical selector.
- Generic actions first; brand/device mappings belong in configuration.
- Physical state from hardware, configuration from flash, device state from devices, ephemeral state from RAM.
- Prefer iPad-first development and simple local tools.
- Keep Wi-Fi credentials and other secrets separate from public configuration.
- Prototype a small onboard HTML/XML editor; keep iOS Shortcuts available as an optional client.
- Keep ordinary configuration separate from firmware updates.
- Implement and measure sleep behavior before making battery-life promises.
- Preserve the first-action goal for light sleep, but permit wake-only first press after deep sleep.
- OLED before buttons; hardware pins and wake capabilities must be verified.
- Do not build a giant device-state machine.
- Add complexity only when a real use case requires it.
